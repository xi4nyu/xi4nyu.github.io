## 结论先行（五条）

1. 他的语言是**「平铺直叙 + 日常词 + 结构标记」**三件套：人称极简（我 / 我们 / 你，0 次「笔者/读者/大家/您」），情绪极低（四篇正文**感叹号 0 个、省略号 0 个、句内加粗 0 处**），全部修辞预算投在「把抽象概念翻译成日常经验」上。
2. **节奏是长短交替的三段式**：短句（<15 字）起头或收束 → 长句（40–70 字）承担解释 → 短句/一句收束；段落极短，段句比接近 1:1，一句一段是常态。
3. **比喻是显式映射，从不留白**：「它就像…/背后的含义就是…/这好比…/这代表…/这就叫…/这种做法叫做…」。且比喻只用于无直观对象的概念；一旦进入可演算的内容（《关于2的补码》），比喻降到几乎为零，改用竖式。
4. **连接词是四件套**：所以 / 因此 / 也就是说 / 但是。「也就是说」是他最高频的「换一种说法」标记；「换句话说、不过、事实上、综上所述、由此可见」在四篇正文中出现 0 次（「换言之」1 次）。
5. **他强调结构与边界，不强调情绪与权威**：加粗＝小标题，引号＝被定义的术语，冒号＝下定义/引清单/给外文；对冲只用范围词（一般来说、主要、一般都），认知边界直接明说（「以目前的信息无法确知」），进入证明则给强断言（「这就证明了…」）。

### 1.3 如何称呼读者：用「你」，且多数时候连称呼都省掉

- 「你」共 3 次：「不知道你怎么看，反正我觉得很奇怪」（补码）、「随便找一本《计算机原理》，都会告诉你」（补码）、「如果数字证书记载的网址，与你正在浏览的网址不一致」（数字签名）。
- 「您」**0 次**、「读者」**0 次**、「大家」**0 次**（四篇正文）。
- 更常见的是**无主语的祈使句**，第二人称隐含在动词里： 「请看下面这段代码（来源）。」「请回忆一下小学算术」「作为一条规则可以记住，所有的对象都存放在heap。」「现在，再来看2的补码表示法。」「还是以-8作为例子。」「举例来说」「注意，这是一个9位的二进制数。」
- **旁证（不计入统计）**：同页 2022 年文章摘要用的是「大家」——「今天谈谈一个重要的计算机概念，大家可能都听说过它，但是很少深究，那就是字节序（Endianness）。」说明「大家」是他后来的用法，这四篇里没有。

### 2.4 他确实交替，而且是固定套路

**套路 C：短过渡句 → 长推演**
> 「接下来，分成两种情况讨论。」→ 紧接长句证明（补码）
> 「还是以-8作为例子。」→ 紧接竖式（补码）

**套路 D：设问 → 一句「回答是」的短答 → 长解释**
> 「接下来的问题是，当Method1方法运行结束，会发生什么事？」

**套路 E：短句并列推进（比喻篇专用）**
> 「一个车间里，可以有很多工人。他们协同完成一个任务。」
> 「线程就好比车间里的工人。一个进程可以包括多个线程。」（进程与线程）

## 4. 比喻与类比（穷尽清单）

### A.《进程与线程的一个简单解释》——比喻密度最高，10 处，一条主线到底

| # | verbatim | 喻体 → 本体 |
|---|---|---|
| 1 | 「计算机的核心是CPU，它承担了所有的计算任务。它就像一座工厂，时刻在运行。」 | 工厂 → CPU |
| 2 | 「假定工厂的电力有限，一次只能供给一个车间使用。也就是说，一个车间开工的时候，其他车间都必须停工。背后的含义就是，单个CPU一次只能运行一个任务。」 | 电力 → 单任务约束 |
| 3 | 「进程就好比工厂的车间，它代表CPU所能处理的单个任务。任一时刻，CPU总是运行一个进程，其他进程处于非运行状态。」 | 车间 → 进程 |
| 4 | 「一个车间里，可以有很多工人。他们协同完成一个任务。」 | 工人 → 线程（铺垫） |
| 5 | 「线程就好比车间里的工人。一个进程可以包括多个线程。」 | 工人 → 线程 |
| 6 | 「车间的空间是工人们共享的，比如许多房间是每个工人都可以进出的。这象征一个进程的内存空间是共享的，每个线程都可以使用这些共享内存。」 | 车间空间/房间 → 进程内存 |
| 7 | 「可是，每间房间的大小不同，有些房间最多只能容纳一个人，比如厕所。里面有人的时候，其他人就不能进去了。这代表一个线程使用某些共享内存时，其他线程必须等它结束，才能使用这一块内存。」 | 厕所 → 独占内存（临界区） |
| 8 | 「一个防止他人进入的简单方法，就是门口加一把锁。先到的人锁上门，后到的人看到上锁，就在门口排队，等锁打开再进去。这就叫"互斥锁"（Mutual exclusion，缩写 Mutex），防止多个线程同时读写某一块内存区域。」 | 门锁＋排队 → mutex |
| 9 | 「还有些房间，可以同时容纳n个人，比如厨房。也就是说，如果人数大于n，多出来的人只能在外面等着。这好比某些内存区域，只能供给固定数目的线程使用。」 | 厨房 → 限定并发数的资源 |
| 10 | 「这时的解决方法，就是在门口挂n把钥匙。进去的人就取一把钥匙，出来时再把钥匙挂回原处。后到的人发现钥匙架空了，就知道必须在门口排队等着了。这种做法叫做"信号量"（Semaphore），用来保证多个线程不会互相冲突。」 | 钥匙架 → semaphore |

**关键修辞特征：映射标记词全部显式写出，从不留隐含比喻。** 他的标记词清单是：`它就像` / `背后的含义就是` / `就好比` / `这象征` / `这代表` / `这就叫` / `这好比` / `这种做法叫做`。读者永远不会自己猜「刚才那个比喻对应什么」。

### B.《Stack的三种含义》——一个意象复用三次（积木）

1. 「在这种数据结构中，数据像积木那样一层层堆起来，后面加入的数据就放在最上层。」 → 积木 = LIFO 存放
2. 「stack的第二种含义是"调用栈"（call stack），表示函数或子例程像堆积木一样存放，以实现层层调用。」 → 积木 = 层层调用
3. 「这三次调用像积木一样堆起来，就叫做"调用栈"。」 → 积木 = 调用栈
（意象的延续，仍不脱离「上下层」： 「程序运行的时候，总是先完成最上层的调用，然后将它的值返回到下一层调用，直至完成整个调用栈，返回最后的结果。」）

### C.《关于2的补码》——几乎零比喻，改用算式类比

唯一一处类比：
- 「请回忆一下小学算术，如果被减数的某一位小于减数，我们怎么办？很简单，问上一位借1就可以了。」 → 小学借位 = 二进制借位

其余全部是竖式推演，verbatim：
> 　０００１００００
> ＋１０００１０００
> －－－－－－－－－
> 　１００１１０００

**这是重要的边界证据**：概念抽象、无直观对象时他才打比方；一旦内容可以逐步演算，他立刻放弃比喻、改用算式。

### D.《数字签名是什么？》——不是比喻，是「人物 + 情节」的拟人化叙事（且为译文）

- 「鲍勃有两把钥匙，一把是公钥，另一把是私钥。」
- 「鲍勃把公钥送给他的朋友们----帕蒂、道格、苏珊----每人一把。」
- 「复杂的情况出现了。道格想欺骗苏珊，他偷偷使用了苏珊的电脑，用自己的公钥换走了鲍勃的公钥。」
- 「后来，苏珊感觉不对劲，发现自己无法确定公钥是否真的属于鲍勃。她想到了一个办法，要求鲍勃去找"证书中心"（certificate authority，简称CA），为公钥做认证。」

特征：给抽象实体配角色（鲍勃/苏珊/道格/帕蒂）＋制造冲突情节（「道格想欺骗苏珊」），用故事推进定义。**此框架来自原文作者 David Youd，非他的原创。**

### E. 比喻的护栏（他自设的）

正文里只承诺「易懂」，不承诺「准确」： 「最近，我读到一篇材料，发现有一个很好的类比，可以把它们解释地清晰易懂。」
**旁证（他本人的留言回复，非正文，不计入统计）**：「这篇文章的比喻，确实不是完全准确。但是，进程和线程要找到现实生活中准确的对应，恐怕很困难吧。」

## 5. 提问与设问

### 5.1 设问可以直接当小标题

《关于2的补码》五级加粗小标题中，**三个是问句**：
- 「**负数在计算机中如何表示？**」
- 「**什么是2的补码？**」
- 「**为什么正数加法适用于2的补码？**」

### 5.2 设问 → 下一段立刻回答，且用显式应答词

| 问（verbatim） | 答（verbatim） |
|---|---|
| 「举例来说，+8在计算机中表示为二进制的1000，那么-8怎么表示呢？」 | 「很容易想到，可以将一个二进制位（bit）专门规定为符号位，它等于0时就表示正数，等于1时就表示负数。」 |
| 「请问哪一种表示法在加法运算中更方便？」 | 「随便写一个计算式，16 + (-8) = ?」 |
| 「如果被减数的某一位小于减数，我们怎么办？」 | 「很简单，问上一位借1就可以了。」 |
| 「接下来的问题是，当Method1方法运行结束，会发生什么事？」 | 「回答是整个stack被清空，i、y和cls1这三个变量消失，因为它们是局部变量……」 |
| 「为什么要采用这么麻烦的方式表示负数，更直觉的方式难道不好吗？」 | 停顿一句（「昨天，我在一本书里又看到了这个问题……」）后，由小标题「**2的补码的好处**」作答 |

注意三种应答起句：**「回答是…」/「很简单，…就可以了」/「很容易想到，…」** —— 他从不让设问悬空超过一段。

### 5.3 反例：并非每篇都设问

《进程与线程的一个简单解释》与《数字签名是什么？》正文设问为 0（数字签名篇仅 1 个「？」，是句末的嵌引疑问「它用图片通俗易懂地解释了，"数字签名"（digital signature）和"数字证书"（digital certificate）到底是什么。」）。

## 6. 强调手段

### 6.1 加粗：只做小标题，0 处句内加粗

四篇正文的 `<strong>` 共 **9 处，全部是独立成行的小标题**；`<em>` **0 处**。

- Stack：「含义一：数据结构」「含义二：代码运行方式」「含义三：内存区域」
- 补码：「负数在计算机中如何表示？」「什么是2的补码？」「2的补码的好处」「2的补码的本质」「为什么正数加法适用于2的补码？」
- 数字签名：「数字签名是什么？」
- 进程与线程：**0 处**（改用阿拉伯数字 1.–11. 分节，配合配图）

### 6.2 引号：标记「正在被定义的术语」，不做反讽

- 「它的中文名字叫做"栈"。」
- 「这就叫做"后进先出"。」
- 「stack的第二种含义是"调用栈"（call stack）」
- 「鲍勃给苏珊回信，决定采用"数字签名"。」
- 「要求鲍勃去找"证书中心"（certificate authority，简称CA）」
- 「这就叫"互斥锁"（Mutual exclusion，缩写 Mutex）」
- 「这种做法叫做"信号量"（Semaphore）」
- 「有"受信任的根证书颁发机构"列表。」

### 6.3 破折号：全篇仅 1 句、2 处

- 「鲍勃把公钥送给他的朋友们----帕蒂、道格、苏珊----每人一把。」（数字签名译文，写作 `----`）
- 其余三篇破折号 **0 处**。

### 6.4 冒号：最高频的组织手段（stack 15 / 补码 10 / 数字签名 8 / 进程 5）

三种固定用途：
1. **下定义、给结论**：「它们的主要区别是：stack是有结构的，每个区块按照一定次序存放，可以明确知道每个区块的大小；heap是没有结构的，数据可以任意存放。」「根据上面这些区别，数据存放的规则是：只要是局部的、占用空间确定的数据，一般都存放在stack里面，否则就放在heap里面。」
2. **引出清单**：「操作系统的设计，因此可以归结为三点：」→「（1）……；（2）……；（3）……」
3. **引出术语外文**：「特点为LIFO，即后进先出（Last in, first out）。」「下面，我们看一个应用"数字证书"的实例：https协议。」

**结论：他强调的是「结构」而非「情绪」。** 加粗＝分节，引号＝定义，冒号＝展开；没有任何一处排版在表达「这很重要 / 这很惊人」。

## 8. 不确定性表达

### 8.1 对冲只用「范围词」，不用「可信度词」

- 「一般来说」3 次，全在 Stack，且全部用于给规则划范围：
  - 「一般来说，系统会划分出两种不同的内存空间：一种叫做stack（栈），另一种叫做heap（堆）。」
  - 「一般来说，每个线程分配一个stack，每个进程分配一个heap」
  - 「因此，一般来说，内存泄漏都发生在heap」
- 「一般都」：「只要是局部的、占用空间确定的数据，一般都存放在stack里面，否则就放在heap里面。」
- 「主要」用作范围限定：「主要为下面这些。」「它们的主要区别是：……」「其他的区别还有，一般来说……」
- 「可能」：「如果数字证书记载的网址，与你正在浏览的网址不一致，就说明这张证书可能被冒用」

### 8.2 认知边界直接明说，而不是用模糊词掩盖

- 「指针变量占用的大小是确定的，但是对象实例以目前的信息无法确知所占用的内存空间大小。」
- 「我对这些问题的理解，一直是模模糊糊的，很多细节搞不清楚。」

### 8.3 进入推理时反而给强断言

- 「这就证明了，在正常的加法规则下，可以利用2的补码得到正数与负数相加的正确结果。」
- 「现在总算彻底搞明白了。」
- 「显然，这是错误的答案。」

### 8.4 0 次出现

「通常」0、「据说」0、「不一定」0、「也许」0、「大概」0、「个人认为」0、「仅供参考」0（均为四篇正文）。

**规范提炼**：对冲的粒度是**范围**（一般来说 / 主要 / 都），不是**可信度**（据说 / 也许）；材料之外的事实明说「以目前的信息无法确知」；自己的推理链给强断言。

## 9. 标点与排版习惯

1. **全角标点**：正文标点全为全角 ，。：；？！（）《》、；半角只出现在代码、算式、URL 内。
2. **引号体例（已逐字核验原始 HTML）**：中文术语用 **ASCII 直双引号 `"…"`（U+0022）**；`U+201C/U+201D` 计数 0；**直角引号「」计数 0**（整页为 0）。例：「它的中文名字叫做"栈"。」——线上现状如此，可能是站点迁移/编码转换所致，但这是可核验的事实。
3. **中文与拉丁字母/数字之间默认不加空格**（2009–2013 年的习惯）：
   - 不加空格：「stack的第一种含义」「特点为LIFO」「一段Java代码」「生成一个Student的实例」「用Hash函数」「简称CA」「https协议」「在8位机中」「n=1时」「mutex是semaphore的一种特殊情况（n=1时）」
   - 少量加空格的**不一致**例子：「共包含了三个变量：i, y 和 cls1。」（半角逗号＋空格）、「16的二进制表示是 00010000」、「即 Z = X + (11111111-Y) + 1」、「（Mutual exclusion，缩写 Mutex）」
   - **同一篇内两种写法并存**：「i, y 和 cls1」与「i、y和cls1」都出现在 Stack 一篇里。
   - **旁证（不计入统计）**：同页 2022 年文章摘要已统一加空格（「通过 DNS 查询，得到域名的 IP 地址」），说明「不加空格」是这批旧文的习惯，不是他的恒常规则。
4. **括号专用于「术语首现给外文 / 简称 / 限定」**：
   - 「（Last in, first out）」「（call stack）」「（bit）」「（Two's Complement）」「（digest）」「（signature）」「（certificate authority，简称CA）」「（Digital Certificate）」「（process）」「（thread）」「（garbage collector）」「（Mutual exclusion，缩写 Mutex）」「（Semaphore）」
   - 限定用：「（n=1时）」「（8位机）」「（被减数）」「（减数）」「（浏览器）」
5. **句末与文末习惯**：
   - 四篇正文**全部以「（完）」结束**，单独一行。
   - **感叹号 0 个**（全角 ！ 与半角 ! 在四篇正文中均为 0），**省略号 0 个**。
   - 问号只在真设问处：补码 7、数字签名 1、Stack 1、进程与线程 0。
6. **版式习惯**：
   - 小标题＝加粗独立成段；代码用 `<pre>`（Stack 2 个代码块）、列表用 `<ul>`（push/pop/top/isempty 四项）、引文用引用块（Stack 3 个）。
   - 数学竖式用**全角数字 + 全角符号 + 全角前导空格**对齐，verbatim：「　０００１００００ / ＋１０００１０００ / －－－－－－－－－ / 　１００１１０００」
   - 分节编号三套：加粗标题（Stack、补码）、阿拉伯数字 1.–11./1.–20.（进程、数字签名，配合配图）、「（1）（2）（3）」（进程结尾三点总结）。
   - 段落极短，段句比≈1:1；**无一段超过 3 句**。
   - 外链写法：正文内嵌链接，必要时括注「（来源）」——「下面以一段Java代码为例（来源）。」「请看下面这段代码（来源）。」「文中涉及的密码学基本知识，可以参见我以前的笔记。」

## 11. 禁止项：他 conspicuously 不做什么（每条附证据）

1. **不做营销腔**。标题是朴素名词/问句：「Stack的三种含义」「数字签名是什么？」「关于2的补码」「进程与线程的一个简单解释」；开头平铺直叙：「学习编程的时候，经常会看到stack这个词」「问一个基本的问题。」；正文 0 处「干货 / 必看 / 手把手 / 史上最全 / 一文读懂 / 深度好文」式推销词。

5. **不训导读者**。0 处「你必须 / 切记 / 一定要 / 严禁」。提醒只用「注意，这是一个9位的二进制数。」「这里要强调的是，只要鲍勃的私钥不泄露，这封信就是安全的」。
6. **不写免责套话**。0 处「仅供参考 / 仅代表个人观点 / 不喜勿喷 / 侵删」。

10. **不写长段、不写无编号长清单**。段句比≈1:1，无一段超过 3 句；超过 3 项的并列一定编号（1.–11.、「（1）（2）（3）」、push/pop/top/isempty 列表）。

## 12. 可直接落地的「技术博客写作标准」（从他身上提炼）

1. **人称**：自称「我」讲经历与判断，用「我们」带读者一起推理；对读者直接说「你」；其余场合省主语用祈使句。禁「笔者 / 读者 / 大家 / 您」。
2. **节奏**：一句一段为主，段句比≈1:1；短句（<15 字）起头或收束，长句（40–70 字）承担解释；短长比约 1:5；四篇的固定套路是「短句起头 → 长句展开 → 短句收束」。
3. **口语词白名单**：其实、也就是说、一般来说、所以、因此、但是、注意、这时、随便、反正、搞、请看、可以看到、举例来说、比如、很简单、不难看出。**黑名单**：说白了、换句话说（改用「换言之」）、事实上、不过、综上所述、由此可见、众所周知。
4. **比喻**：抽象概念必须给一个日常类比，并**显式写出映射**（它就像 / 背后的含义就是 / 这好比 / 这代表 / 这就叫 / 这种做法叫做）；一个意象可以复用（积木用了 3 次）；**能给算式就不打比方**。
5. **设问**：有推导链的文章用设问驱动，问句可直接当小标题；回答必须在下一段内出现，且用「回答是… / 很简单，…就可以了 / 很容易想到，…」起句。
6. **强调只做三件事**：加粗＝小标题，引号＝被定义的术语，冒号＝下定义/引清单/给外文。不用句内加粗、不用斜体、**不用感叹号**、不用省略号。
7. **术语处理**：首现写「中文（English）」，简称写「（全称，简称XX）」；每节收尾给一句「也就是说 / 换言之」的复述。
8. **确定性与对冲**：对冲只用范围词（一般来说、主要、一般都）；认知边界明说（「以目前的信息无法确知」）；结论句给强断言（「这就证明了…」）。禁「据说 / 也许 / 不一定」式含糊，禁「仅供参考」式免责。
9. **标点排版**：全角标点；中文与拉丁字母/数字之间不加空格；引号包术语；数学竖式用全角字符对齐；外链内嵌并括注「（来源）」。
10. **收尾**：正文最后一行写「（完）」。
