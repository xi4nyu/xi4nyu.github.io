# 技术博客写作规范（阮一峰风格）

> 本规范从阮一峰网络日志（ruanyifeng.com）的技术文章中提炼，用于指导技术博客的写作与审校。
> 语料范围与置信度见文末「附录：证据来源」。

**怎么用**：写之前看「零、总纲」和「一、选题」；写完看「十四、发布前检查清单」。文中标 ✅ 的是可直接照做的规则，标 ❌ 的是禁止项；标「规范要求」的条目是原站没做到、但本规范要求补上的。

---

## 零、一句话总纲

**一篇文章只讲一件事，用最短的路径把它讲清楚。**

作者本人把这条讲得最直白（《科技爱好者周刊》第 288 期）：

> 很简单，就是一句话：**文章采用单线结构**。
>
> 所谓"单线结构"（也称"线性结构"），指的是一篇文章只说一件事，按照线性顺序进行叙述，由浅入深、循序渐进、平铺直叙、层层递进。

他还给出了判断标准：

> 技术写作的好坏，跟语文水平关系不大，更多是一个技巧问题。
>
> 因为技术写作的评价标准，不是艺术性，而是表达是否清楚明白。它不需要华丽的词藻、巧妙的比喻、深刻的感悟，只需要把问题说清楚。
>
> **把问题说清楚的关键，在于你的思想是否清楚。**

由此推出三条不可动摇的原则：

| 原则 | 含义 | 违反的后果 |
|---|---|---|
| 单线 | 一篇一个论点，一条线走到底 | 读者迷路，不知道你在讲哪件事 |
| 具体 | 抽象概念必须落到可感、可算、可复现的东西上 | 读者看懂了每个字，却没懂这件事 |
| 先想清楚 | 想不清楚就不要动笔，先拆问题 | 写成思维导图，不是文章 |

## 一、选题

### 1.1 选题的入口：一个真实的疑问

好的选题来自"大家都遇到过、但资料没讲清"的地方。开篇常常直接把这个疑问摆出来：

> 《计算机原理》课本说，启动时，主引导记录会存入内存地址0x7C00。
>
> 这个奇怪的地址，是怎么来的，课本就不解释了。我一直有疑问，为什么不存入内存的头部、尾部、或者其他位置，而偏偏存入这个比 32KB 小1024字节的地方？

规则：

- 选题必须能写成一个问句。写不成问句，说明你还没想清楚要讲什么。
- 优先选"常见资料语焉不详"的点，而不是"资料已经很丰富"的点。
- 允许小题大做：一个内存地址的来历，可以是一篇文章。

### 1.2 三类主力选题

| 类型 | 标题特征 | 例子 |
|---|---|---|
| 概念是什么 | `XX 是什么`／`理解 XX` | 《理解inode》《CAP 定理的含义》 |
| 原理怎么运作 | `XX 原理`／`XX 的工作过程` | 《DNS 原理入门》《编译器的工作过程》 |
| 一个具体疑问 | 疑问句 | 《为什么主引导记录的内存地址是0x7C00？》 |

### 1.3 一篇只解决一个问题

问题太大就拆篇。作者明确主张：

> 这时，建议把这个问题拆分成多篇文章，每篇文章保持单线结构，坚持做到一篇文章只讲一点，而且争取把这一点讲透。

拆篇的两种做法：

- **续篇制**：《RSA算法原理（一）》《RSA算法原理（二）》《SSH原理与运用（一）（二）》。
- **分层制**：先发"入门"，再发"详解"（《DNS 原理入门》2016 → 《DNS 查询原理详解》2022）。

## 二、标题

### 2.1 可用句式

- `XX 入门教程` —— 信息论入门教程、汇编语言入门教程
- `XX 原理详解` / `XX 原理入门` —— DNS 查询原理详解、DNS 原理入门
- `理解 XX` —— 理解字节序、理解inode、理解Linux系统负荷
- `XX 的工作过程` / `XX 的启动流程` —— 编译器的工作过程、Linux 的启动流程
- `A，B 和 C 的区别` —— IaaS，PaaS，SaaS 的区别
- `A 与 B 的比较` —— 字节序探析：大端与小端的比较
- 疑问句 —— 为什么寄存器比内存快？

### 2.2 硬性要求

1. **标题必须等于内容。** 这是最容易犯的错，而且读者会立刻发现。
   反例（真实发生）：《编译器的工作过程》实际讲的是 C 程序的构建流程，留言区有大量批评——

   > 文不对题：希望的结果是解释编译器的*编译*环节的机理，看到的结果确实一个包含了构建脚本、预处理、编译、链接、安装、装载执行的过程。

   标题一旦承诺了范围，正文就必须交付这个范围。交付不了，就改标题。

2. **标题里出现的术语，正文必须解释。** 反之，正文的重点必须在标题里出现。
3. **中英文之间加空格**：`DNS 查询原理详解`、`理解 Linux 系统负荷`。
4. **长度一般 5–15 字**（实测四篇：5、7、10、14 字）；教程型可以到 20 字左右（《如何验证 Email 地址：SMTP 协议入门教程》）。不用副标题堆砌，不用"浅谈""漫谈""那些事"。
5. 不承诺你做不到的事：不写"一文搞懂""彻底讲透"。
6. **同一主题写第二遍时，用副标题把新范围钉死**，与旧文区分。例：2016《理解字节序》→ 2022《字节序探析：大端与小端的比较》。

## 三、开篇

开篇只有一件事：**让读者确认"这说的就是我的问题"，然后知道这篇文章会怎么解决它。**

### 3.1 开篇要做的三件事

开篇通常只有 1–3 句，必须在这几句里完成三件事：

| 任务 | 说明 | 逐字示例 |
|---|---|---|
| 点题 | 说出主题词，并给出英文名 | "今天谈谈一个重要的计算机概念，大家可能都听说过它，但是很少深究，那就是字节序（Endianness）。" |
| 说价值 | 讲清为什么值得看 | "inode 是一个重要概念，是理解 Unix/Linux 文件系统和硬盘储存的基础。" |
| 交代动因／划界 | 我从哪看来的；本文讲什么、不涉及什么 | "最近，我读到一篇材料，发现有一个很好的类比，可以把它们解释地清晰易懂。" |

三件事齐全的完整例子（《编译器的工作过程》开篇连续三段）：

> 源码要运行，必须先转成二进制的机器码。这是编译器的任务。
>
> 这些命令到底在干什么？大多数的书籍和资料，都语焉不详，只说这样就可以编译了，没有进一步的解释。
>
> 本文将介绍编译器的工作过程，也就是上面这三个命令各自的任务。我主要参考了Alex Smith的文章《Building C Projects》。需要声明的是，本文主要针对gcc编译器，也就是针对C和C++，不一定适用于其他语言的编译。

**降低读者压力的技巧**：承认自己也曾经不懂。例："我一直搞不清楚，这个过程到底是怎么回事……这几天，我查了一些资料，试图搞懂它。下面就是我整理的笔记。"

### 3.2 其他可用的开场

- **直接下定义**（适合概念辨析）："标题里面的三个术语，很容易混淆，专业人员有时也会用错。本文就用图片解释它们有何区别。"
- **历史事件**（适合原理溯源）："1992年，美国佐治亚州的WEB Technology公司，宣布做出了重大的技术突破。"
- **限定演示对象**（适合实操）："网上有很多公用的 DNS 服务器，这篇文章选择 Cloudflare 公司提供的 1.1.1.1 进行演示。"

不用故事、不用新闻由头、不预告目录。

### 3.3 开篇禁用

- ❌ "随着互联网的飞速发展……"
- ❌ 行业大势、时代背景、个人感想
- ❌ 悬念式开头（"你可能想不到……"）
- ❌ 先讲自己研究了多久、踩了多少坑

## 四、结构

### 4.1 单线结构

一条主线，从入口到出口，中间不岔路。作者的原话：

> 这就好比一个游览区，只有一条游览路线，从入口到出口，跟着箭头一路走，就能看到所有景观，非常明白清楚。

> 只要采用了单线结构，技术文章就不会太差。即使内容是难懂的，至少结构是清晰的，一环扣一环，读者能知道自己卡在哪一环上。

### 4.2 编号推进

正文用编号切分，读者随时知道自己在第几步。两种体系：

- **中文数字大节**：`零、boot 的含义` → `一、第一阶段：BIOS` → ……；一级可以从「零」起，大节内用阿拉伯小节 `1.1 硬件自检`。
- **步骤式**：`第一步 配置（configure）` → `第二步 确定标准库和头文件的位置` → …… → `第十一步 动态连接`。

规则：

- 每个编号块只解决一个问题。
- 小节标题就是这个块的**对象**或**结论**，用名词短语，不用完整句，不用"关于 XX 的一些说明"。
- 编号的粒度保持一致，不出现"第七步"里再套三层。
- 编号节数实测 6–12 个；超过 12 节考虑拆篇。

### 4.3 步骤讲解的三段式

讲一个多步流程，先讲"为什么是这几步"，再列清单，再逐步演示：

> 这种树状结构的意义在于，**只有上级域名，才知道下一级域名的 IP 地址，需要逐级查询。**
>
> 所以，如果想要查询二级域名 `es6.ruanyifeng.com` 的 IP 地址，需要三个步骤。
>
> 第一步，查询根域名服务器……
>
> 下面依次演示这三个步骤。

**清单与演示必须 1:1 对应**：清单里三步，正文里就得有三个对应的小节，不多不少。

### 4.4 篇幅

实测四篇正文汉字数：724、1628、1883、1996。

| 类型 | 汉字数 | 编号节数 | 配图密度 |
|---|---|---|---|
| 单点速答型 | 700–1000 | 6 左右 | 约 350 字/图 |
| 概念详解型 | 1500–2000 | 8–12 | 100–400 字/图 |
| 步骤流程型 | 2000–3000 | 10 步以上 | 按需 |

- 低于 700 字说明没讲透，高于 3000 字说明该拆篇。
- 一篇讲一件事。第二件事就是下一篇文章。

## 五、段落与句子

### 5.1 段落

实测四篇：段落平均 30–39 汉字，中位 22–37，即**一段 2–3 行**。

- **一段 1–3 句**，平均 1.4 句/段，段句比接近 1:1。**实测没有一段超过 3 句。**
- **单句成段是常态**，实测占 55%–63%。逐字示例：

  > 理解这一点，才能理解计算机如何处理字节序。

  > 至此，全部启动过程完成。

  > 所以，比较大小时，小端序有优势。

- **关键结论单独成段**，前后空行。示例：

  > **所以，主引导记录就是引导"操作系统"进入内存的一段小程序，大小不超过1个扇区（512字节）。**

- 长段上限 90–120 汉字，只允许出现在连续推导处。
- 一段只说一个意思。出现第二个"但是"就另起一段。
- 引出下文的句子用全角冒号结尾：

  > 可以用stat命令，查看某个文件的inode信息：

### 5.2 句子

实测四篇：平均句长 31–40 字，中位 25–32 字。**主力是 25–40 字的中句**，既不是短句体，也不是长句体。

| 句长 | 作用 | 逐字示例 |
|---|---|---|
| < 15 字 | 起头或收束 | "问一个基本的问题。"／"什么是2的补码？"／"还是以-8作为例子。"／"显然，这是错误的答案。" |
| 25–40 字 | 主力，承担叙述与解释 | — |
| 40–70 字 | 交代因果、列举条件 | "也就是说，在这种情况下，正常的加法规则不适用于正数与负数的加法，因此必须制定两套运算规则，一套用于正数加正数，还有一套用于正数加负数。" |

固定节奏：**短句起头 → 中长句展开 → 短句收束。**

- 一个句子只承担一个逻辑转折。
- 少用从句套从句。英文的长定语从句，翻成中文要拆开。
- 加粗只用于结构，不用于句内强调（见 5.3）。

### 5.3 加粗规则

加粗**只用于结构，不用于情绪**。实测两种用法，与年代相关：

| 年代 | 用法 | 逐字示例 |
|---|---|---|
| 2009–2013 | 加粗 = 小标题，独立成行；**句内加粗 0 处** | "**负数在计算机中如何表示？**"（《关于2的补码》全篇加粗均为小标题） |
| 2014 之后 | 加粗 = 定义句或结论句 | "**SaaS 是软件的开发、管理、部署都交给第三方，不需要关心技术问题，可以拿来即用。**" |

规则：

- 加粗只承担三件事：**小标题、定义句、结论句**。
- 不加粗术语名、普通强调、情绪词。
- **不用斜体。**
- 一段最多一处加粗。
- 加粗句必须能独立读懂。

### 5.4 引用块（`>`）只装非叙述性内容

引用块用于：**他人引语、清单、命令、代码**。正文散文永远不放进引用块。

| 用途 | 示例 |
|---|---|
| 引语 | 英文谚语、他人原话 |
| 清单 | 编号或项目符号列表 |
| 命令 | `$ stat test.txt` |
| 代码 | 代码块 |

规则：

- 一段叙述如果放进引用块，就是排版错误。
- 引用块里的清单条目要与正文用词一致。
- 引用块不承担主论点，主论点必须在正文里说出来。
- 引用块内部需要缩进时，用全角空格，保持中文排版整齐。

## 六、语言

### 6.1 人称

| 人称 | 分工 | 逐字示例 |
|---|---|---|
| 我 | 讲个人经历、个人判断 | "今天，我读到一篇好文章。"／"我对这些问题的理解，一直是模模糊糊的。" |
| 我们 | 作者＋读者一起推理，**不是"我方"** | "请回忆一下小学算术，如果被减数的某一位小于减数，我们怎么办？" |
| 你 | 直接称呼读者，用得很少 | "不知道你怎么看，反正我觉得很奇怪" |
| 省主语 | 最常用，用祈使句指路 | "请看下面这段代码（来源）。"／"还是以-8作为例子。"／"注意，这是一个9位的二进制数。" |

规则：

- 自称只用"我"，**不用"笔者"**（实测 0 次）。
- "我们"只在与读者共同推理时使用，不用来指代团队或立场。
- **避免"读者""大家""您"**。"大家"仅在近年口语化开头里偶见（"大家可能都听说过它"），不作常规称呼。
- 指路优先用无主语祈使句，而不是"你应该……"。

### 6.2 连接词

主力是**四件套：所以、因此、也就是说、但是**。实测频率（4 篇正文）：

| 连接词 | 作用 | 说明 |
|---|---|---|
| 也就是说 | 换一种说法 | 最高频的复述标记 |
| 所以 | 推论 | 推导密集的文章里单篇可达 10 次以上 |
| 因此 | 结论 | 可后置于主语："操作系统的设计，因此可以归结为三点：" |
| 但是 | **唯一的转折词** | 不用"不过""然而" |

次常用：**其实、注意、一般来说、举例来说、比如、这时、换言之、实际上**。

**避免**（实测 0 次，或另有更常用的替代）：

- ❌ 换句话说 → 用 **换言之**
- ❌ 事实上 → 用 **实际上**
- ❌ 这是因为 → 原因用"因为"后置："变量消失，因为它们是局部变量"
- ❌ 综上所述、由此可见、众所周知、值得注意的是、然而、不过

规则：连接词是路标，不是装饰。每段开头尽量给一个，让读者知道这段与前一段的关系。

### 6.3 观点怎么表达

**不用第一人称声明观点，用标记词 + 加粗断言 + 否定式对照。**

逐字示例：

> 注意，高可用不是指系统不中断（那是容错能力），而是指一旦中断能够快速恢复，即中断必须是短暂的。

> 注意，灾备不是为了挽救基础设置，而是为了挽救业务。

模式：`注意，X 不是 A，而是 B。` —— 先否掉一个常见误解，再给出正解。这是技术文章里最有效的纠偏句式。

### 6.4 术语处理

**首次出现：中文名（English 全称，缩写为 XXX），并把外链挂在术语上。**

实测四种写法，按场景选用：

| 场景 | 写法 | 逐字示例 |
|---|---|---|
| 有通用中文译名 | 中文名（英文全称，缩写为 XX） | "主引导记录"（Master boot record，缩写为MBR） |
| 中文译名生硬 | 英文名（English），简称为 XX | "基本輸出輸入系統"（Basic Input/Output System），简称为[BIOS](...) |
| 只有缩写常用 | 中文名（English），缩写为 XX | "硬件自检"（Power-On Self-Test），缩写为[POST](...) |
| 概念对比 | 引号 + 加粗 +（English，简称 XX） | 这种排列称为"**大端序**"（big-endian，简称 BE） |

规则：

- 外链挂在术语本身，而不是另起一行写"详见"。术语定义优先链维基百科。
- 术语第一次出现给全称和缩写，第二次起只用中文或只用缩写。
- 代码、命令、文件名、变量用行内代码标记：`es6.ruanyifeng.com`、`dig`。
- 同一概念有两个通用名，并列写出："软链接"（soft link）或者"符号链接（symbolic link）"。
- **中英文之间的空格**：原站旧文（2009–2019）多数**不加空格**（"stack的第一种含义""简称CA""在8位机中"），且同一篇内前后不一致（"i, y 和 cls1"与"i、y和cls1"并存）；2022 年后已统一加空格（"通过 DNS 查询，得到域名的 IP 地址"）。**规范要求：全文统一加空格，不混用。**

### 6.5 标点

- 中文全角标点，句末用中文句号。半角只出现在代码、算式、URL 里。
- **引号用来标记"正在被定义的术语"**，不做反讽。例：它的中文名字叫做"栈"；这就叫"互斥锁"（Mutual exclusion，缩写 Mutex）。
- 引号体例：原站正文用的是 **ASCII 直双引号**（实测 U+201C/U+201D 与直角引号「」计数均为 0）。**规范要求：全站统一，推荐中文引号 “ ”，不混用。**
- **冒号是最高频的组织手段**（实测单篇可达 15 处），承担三件事：

  1. 下定义、给结论：

     > 根据上面这些区别，数据存放的规则是：只要是局部的、占用空间确定的数据，一般都存放在 stack 里面，否则就放在 heap 里面。

  2. 引出清单：

     > 操作系统的设计，因此可以归结为三点：

  3. 引出术语外文：

     > 下面，我们看一个应用"数字证书"的实例：https 协议。

- **不用感叹号**（实测 4 篇正文 0 处）；少用省略号；极少用破折号（3 篇为 0，1 篇译文出现 2 处）。
- 问号只用于真设问，不用于情绪化反问。
- 数学竖式用全角数字＋全角符号＋全角前导空格对齐：

  ```
  　０００１００００
  ＋１０００１０００
  －－－－－－－－－
  　１００１１０００
  ```

- 中文与拉丁字母、数字之间的空格见 6.4。

### 6.6 情绪与幽默

- **情绪极低**：不用感叹号，不用网络梗，不用表情符号，全文没有一句玩笑话。
- **幽默来自选材的日常感，不来自修辞夸张**：

  > 可是，每间房间的大小不同，有些房间最多只能容纳一个人，比如厕所。

  > 还有些房间，可以同时容纳 n 个人，比如厨房。

- **允许自曝无知**，用来降低读者压力：

  > 我对这些问题的理解，一直是模模糊糊的，很多细节搞不清楚。

- **情绪一旦露头，立刻被冷静接住**：一句"反正我觉得很奇怪"之后，下一段直接上小标题继续推理。
- **不训导读者**：没有"你必须""切记""一定要"。提醒只用"注意，这是一个9位的二进制数。"
- **不做元话语铺陈**：不写"本文分为三部分""下面进入正题"，第一句就进入主题。

## 七、类比

这是阮一峰技术文章最核心的技术。**抽象概念必须有物理对应物。**

### 7.1 用一套类比承载一组概念

不要给每个概念各找一个比喻，那样读者要记三套东西。正确做法是：**一套场景，多个概念在同一场景里分工。**

| 文章 | 类比 | 承载的概念 |
|---|---|---|
| 《进程与线程的一个简单解释》 | 工厂 / 车间 / 工人 | CPU / 进程 / 线程 |
| 《IaaS，PaaS，SaaS 的区别》 | 披萨店 | 三种云服务模式 |
| 《容错，高可用和灾备》 | 飞机 / 汽车 | 三种可靠性等级 |

逐字示例：

> 计算机的核心是CPU，它承担了所有的计算任务。它就像一座工厂，时刻在运行。

> 进程就好比工厂的车间，它代表CPU所能处理的单个任务。

> 线程就好比车间里的工人。一个进程可以包括多个线程。

**关键在于三个概念共享同一个基座**，差异只体现在"分工不同"或"坏到什么程度"，而不是靠形容词区分：

- 工厂类比的基座是"一座工厂"，三个概念分别在"厂 / 车间 / 工人"三个层级上。
- 飞机汽车类比的基座是"一台交通工具"，三个概念分别对应"坏一个引擎""扎一个轮胎""即将坠毁"三个故障等级。

同一套类比只允许跨越一个维度。跨得太多，读者就要自己猜映射关系，类比就失效了。

**映射必须显式写出，从不留白。**固定的标记词清单：

`它就像` ／ `背后的含义就是` ／ `就好比` ／ `这象征` ／ `这代表` ／ `这就叫` ／ `这好比` ／ `这种做法叫做`

逐字示例：

> 计算机的核心是CPU……它就像一座工厂，时刻在运行。

> 背后的含义就是，单个CPU一次只能运行一个任务。

> 这象征一个进程的内存空间是共享的。

> 这就叫"互斥锁"（Mutual exclusion，缩写 Mutex）。

**一个意象可以复用。**《Stack的三种含义》用"积木"讲了三种含义：数据结构像积木一层层堆起来、子例程像堆积木一样存放、三次调用像积木一样堆起来。同一个意象复用三次，读者只需记住一个画面。

### 7.2 能给算式就不打比方

概念抽象、没有直观对象时才打比方；**一旦内容可以逐步演算，立刻放弃比喻，改用算式**。

《关于2的补码》讲的是可演算的二进制运算，全篇几乎零比喻，只用一句小学借位做引子（"请回忆一下小学算术……很简单，问上一位借1就可以了"），其余全是竖式推演。

**类比不能承载精确的技术断言。**凡是要精确的地方，必须回到术语、定义和算式。

### 7.3 类比之后必须回译

讲完比喻，立刻用术语说一遍，不留映射缺口：

> 上图中，飞机是你的 IT 基础设施，飞行员是你的业务，飞行员弹射装置就是灾备措施。

### 7.4 承认类比的边界

一个类比只能解释一个侧面，讲清它解释什么、不解释什么：

> 这篇文章的比喻，确实不是完全准确。但是，进程和线程要找到现实生活中准确的对应，恐怕很困难吧。
>
> 我的基本想法是：（1）进程是一个容器。（2）线程是容器中的工作单位。

**反面教训（真实发生）**：《进程与线程的一个简单解释》用"工厂电力"比喻 CPU 调度，被读者指出混淆了进程与线程的调度单位——

> 文章的意思是同一个进程的多个线程是同时执行的，cpu的调度单位是进程。但实际是错误的，cpu的调度单位是线程。

正文只承诺"易懂"，不承诺"准确"。发现比喻有偏差，就在后续文章或留言里直接承认。

### 7.5 设问驱动推理

**有推导链的文章用设问推进；有直观模型的文章用类比＋陈述推进。**

- 设问可以直接当小标题：

  > **负数在计算机中如何表示？**

  > **什么是2的补码？**

  > **为什么正数加法适用于2的补码？**

- **设问从不悬空超过一段**，下一段立刻回答，并用显式应答词起句：

  > 问：如果被减数的某一位小于减数，我们怎么办？
  >
  > 答：很简单，问上一位借1就可以了。

  > 问：接下来的问题是，当 Method1 方法运行结束，会发生什么事？
  >
  > 答：回答是整个 stack 被清空……

- 应答起句三选一：`回答是…` ／ `很简单，…就可以了` ／ `很容易想到，…`。
- 设问只用于推进推理，不用于情绪化反问。

## 八、举例、数字与事实

### 8.1 例子必须可复现

优先级：**能跑的命令 > 能算的数字 > 能查的事件 > 生活场景**。

逐字示例（每一步都配真实返回）：

> $ dig @1.1.1.1 es6.ruanyifeng.com

> 在其中找到 ANSWER SECTION 这个部分，它给出了查询的答案，域名对应的 IP 地址是 104.198.14.52。

**失败的返回也是证据**：

> 因为它给不了 `es6.ruanyifeng.com` 的 IP 地址，所以输出结果中没有 ANSWER SECTION，只有一个 AUTHORITY SECTION。

### 8.2 数字给到可复算精度

不要写"大幅压缩"，要写：

> 甲文件的内容50%是a，30%b，20%是c，则平均每个符号要占用1.49个二进制位。
>
> 那么压缩1024个符号，理论上最少需要1526个二进制位，约0.186KB，相当于压缩掉了81%的体积。

规则：给出**输入 → 中间值 → 结果 → 百分比**，让读者能自己验算。

### 8.3 用对称算例做对比

想说明"A 比 B 难"，就给两个结构完全相同的算例，只改一个变量：

> 甲文件……则平均每个符号要占用1.49个二进制位。
>
> 乙文件的内容10%是a，10%是b，……，10%是j，则平均每个符号要占用3.32个二进制位。
>
> 对比上面两个算式，可以看到文件内容越是分散（随机），所需要的二进制位就越长。

**结论从对比里长出来，不要直接断言。**

### 8.4 对比不用表格

要说明"A、B、C 三者的区别"，**优先用结构，不用表格**。三种做法：

1. **同一模板重复三次**：每个对象都按"加粗一句话定义 + 紧随其后的清单"来写，行数与颗粒度保持一致，形成视觉上的对照。
2. **程度不等式**：让同一组维度在多个对象上连续取值，而不是罗列优缺点。

   > 从左到右，自己承担的工作量（上图蓝色部分）越来越少，IaaS > PaaS > SaaS。

3. **两套清单并置**：先按"文中出现顺序"列一遍，再按"正式分类"列一遍，让读者自己看出映射关系。

表格只在真需要逐项对齐多个字段时才用；能用并列清单表达的，就用清单。

### 8.5 事实要有锚点

日期 + 机构 + 人名 + 产品名，构成可核查的事实：

> 它是1948年由美国数学家[克劳德·香农](https://zh.wikipedia.org/wiki/克劳德·香农)（Claude Shannon）在经典论文[《通信的数学理论》](http://cm.bell-labs.com/cm/ms/what/shannonday/shannon1948.pdf)中，首先提出的。

> 根域名服务器全世界一共有13台（都是服务器集群）。

## 九、代码与图

### 9.1 代码

- **最小化**：只给可验证的最小片段，不做完整可运行程序。实测一篇 4 个代码块合计只有 6 行有效代码。
- **三段式**：引导句 → 代码块 → 解释句。禁止"裸贴代码"。
- **引导句用全角冒号或句号结尾**，明确交代"下面是什么"：

  > 可以用stat命令，查看某个文件的inode信息：

  > 举例来说，处理器读入一个16位整数。如果是大端字节序，就按下面的方式转成值。

- **解释句固定以"上面代码中，"开头**：

  > 上面代码中，第一个字节左移8位（即后面添8个`0`），然后再与第二个字节进行或运算。

- **可运行**：命令行示例带 `$` 提示符，并给出预期输出。
- **长代码要截断并声明**：

  > 为了便于阅读，上面代码只截取了头文件中与源码相关的那部分，即fputs和FILE的声明，省略了stdio.h的其他部分（因为它们非常长）。

- 代码块标注语言（bash、clike、js 等）。行内代码用于变量、命令、文件名、域名：`buf`、`0x2211`、`dig`。
- 代码里的注释用英文或中文均可，但要与正文用词一致。

### 9.2 图

- 图承担两件事：**类比的可视化**、**结构的可视化**（层级、流程、内存布局）。
- **图紧跟相关段落，从不堆在文末。**
- **图不加图注**，靠上下文解释。用"如下图""上图是……"把图和正文缝在一起：

  > 同理，`0x1234567`的大端字节序和小端字节序的写法如下图。

  > 上图是大端序排列，因为是从左到右排列，所以三个数字在右边个位数对齐。

- 引用他人的图要给出出处（`via` 或行内链接）。
- 配图密度：约 100–400 字配一张图。概念详解型可以纯图无代码（实测一篇 1628 字配 14 张图）。
- 命令行类文章可以"命令 + 输出截图"成对出现。
- ASCII 图适合展示内存布局，紧凑且可复制：

  +--------------------- 0x400
  | BIOS data area
  +--------------------- 0x5??
  | OS load area

## 十一、边界与不确定性

### 11.1 把边界写进内容，不写免责声明

不要写"本文仅供参考""如有错误欢迎指正"。要**具体说明你选了哪个对象来演示**：

> 网上有很多公用的 DNS 服务器，这篇文章选择 Cloudflare 公司提供的 1.1.1.1 进行演示。

> 命令行工具 dig 可以跟 DNS 服务器互动，我们就用它演示 DNS 查询。如果你还没有安装，可以搜一下安装方法，在 Linux 系统下是非常容易的。

这一句同时限定了：工具（dig）、平台（Linux）、被查询对象，并把"安装方法"明确排除在文章范围外。

### 11.2 对冲只用范围词，不用可信度词

**范围词**（推荐）：`一般来说`、`主要`、`一般都`、`可能`。逐字示例：

> 一般来说，系统会划分出两种不同的内存空间：一种叫做stack（栈），另一种叫做heap（堆）。

> 所以，压缩已经压缩过的文件（递归压缩），通常是没有意义的。

> 本文主要针对gcc编译器，也就是针对C和C++，不一定适用于其他语言的编译。

**可信度词**（避免）：`据说`、`也许`、`大概`、`不一定`（作可信度用时）、`个人认为`。实测 4 篇正文中均为 0 次。

**边界外的内容，直接说明缺什么**，不要用模糊词掩盖：

> 指针变量占用的大小是确定的，但是对象实例以目前的信息无法确知所占用的内存空间大小。

**自己的推理链，反而要给强断言**：

> 这就证明了，在正常的加法规则下，可以利用2的补码得到正数与负数相加的正确结果。

> 显然，这是错误的答案。

### 11.3 不要假装精确

类比不精确就承认（见 7.4）。样本不足就说明样本。数字有时效性就标注时间。

**规范要求（原站缺口）**：涉及版本、清单、命令输出、价格、性能数据的内容，必须标注**时效**（"截至 20XX 年 X 月"）与**版本号**。这是原站未做而应当补上的一条。

## 十二、结尾

结尾必须**收在终点上**，不能停在半路，也不能另起新话题。收法有四种：

1. **总结小节**——长篇（8 节以上）单列一节「总结」，把全文收成一张无框表格：

   > - 容错：发生故障时，如何让系统继续运行。
   > - 高可用：系统中断时，如何尽快恢复。
   > - 灾备：系统毁灭时，如何抢救数据。

2. **行动建议**——给读者一件可以马上做的事：

   > 知道了 DNS 查询的原理，完全可以自己写一个 DNS 的递归服务器，这是不难的。网上有很多参考资料，有兴趣的话，大家可以试试看。

3. **回译总结**——把全文的类比翻回术语（见 7.3）。
4. **讲完即止**——短篇（6 节左右）可以只靠末节自然收束，但最后一句必须是流程或推导的终点：

   > 至此，全部启动过程完成。

   > 32位整数的求值公式也是一样的。

规则：

- **收尾节的有无与篇幅相关**：10 节的长文用「九、总结」+「十、参考链接」；6–8 节的短文末节自然收束。
- **不写套话**。实测四篇中"以上就是"0 次、"下一篇文章"0 次、"小结"0 次。
- 结尾要与开篇的疑问闭环：开头问的那个问题，结尾必须已经答完。
- 正文结束单独一行标 `（完）`。有广告或其他内容插入时，正文用 `（文章完）` 与之区分。

## 十三、禁用清单

写作时逐条自查，命中任何一条就要改：

- ❌ **一篇文章讲两件事**，或中途岔到另一个话题。
- ❌ **标题与内容不符**，标题承诺的范围没交付。
- ❌ **抽象概念没有落地**，全靠形容词和术语堆砌。
- ❌ **用表格代替思考**。原站几乎不用表格，多方对比靠"同一模板重复 + 并列清单 + 不等式"。表格只在真需要逐项对齐时才用。
- ❌ **裸贴代码**，没有引导句和解释句。
- ❌ **把叙述段落放进引用块**。引用块只装引语、清单、命令、代码。
- ❌ **给图加图注**。图靠上下文解释，用"如下图""上图是……"缝合。
- ❌ **"我认为""我觉得"**。观点靠标记词与加粗断言表达。
- ❌ **二手转述当出处**，不引原始文献。
- ❌ **免责声明段**（"本文仅供参考""水平有限"）。
- ❌ **营销腔**：一文搞懂、保姆级、天花板、绝绝子、遥遥领先。
- ❌ **排比抒情**、空洞形容词（"极其强大""非常优雅"）。
- ❌ **悬念式结尾**（"至于为什么，留给大家思考"）。
- ❌ **"以上就是""下一篇文章""小结"** 这类套话。
- ❌ **元话语铺陈**："本文分为三部分""下面进入正题""综上所述""由此可见"。
- ❌ **黑名单连接词**：说白了、想想看、换句话说（用"换言之"）、事实上（用"实际上"）、这是因为、不过、然而、众所周知、值得注意的是。
- ❌ **网络梗、表情符号、感叹号**。实测 4 篇正文感叹号 0 处、省略号 0 处。
- ❌ **训导读者**："你必须""切记""一定要""严禁"。
- ❌ **无时效的数据**：版本号、清单、性能数字不标日期。
- ❌ **长难句**：一句话里超过两个转折。
- ❌ **不解释的术语**：首次出现的外文缩写没有全称。
- ❌ **超长段落**：超过 3 句或超过 120 汉字的段落，除非是连续推导。
- ❌ **无编号的长清单**：并列超过 3 项，必须编号。

## 十四、发布前检查清单

**选题与标题**

- [ ] 这篇文章能用一句话说清讲什么？这句话和标题一致吗？
- [ ] 标题承诺的范围，正文全部交付了吗？
- [ ] 标题是否 5–15 字（教程型可到 20 字）？

**开篇**

- [ ] 第一段是否让目标读者认出自己的问题？
- [ ] 是否交代了动机/来源？
- [ ] 是否划定了范围（讲什么、不涉及什么）？

**结构**

- [ ] 全文是否只有一条主线？有没有岔路？
- [ ] 每节是否只解决一个问题？节标题是否指向明确？
- [ ] 多步流程是否做到"为什么 N 步 → N 步清单 → 1:1 演示"？
- [ ] 篇幅是否在 700–3000 汉字？超了要不要拆篇？

**内容**

- [ ] 每个抽象概念是否都有物理对应物？映射标记词（它就像／背后的含义就是／这好比）是否显式写出？
- [ ] 类比之后是否回译成术语？有没有用类比承载精确断言？
- [ ] 可演算的内容是否改用算式，而不是硬打比方？
- [ ] 有推导链的文章是否用设问驱动？设问是否在下一段内就作答？
- [ ] 是否有至少一个可复现的例子（命令、算例、可查事件）？
- [ ] 数字是否给到可复算精度，并附中间值？
- [ ] 是否用对称算例做对比，而不是直接断言结论？

**语言**

- [ ] 段落是否都在 1–3 句、平均 30–40 汉字？关键结论是否单独成段？
- [ ] 单句成段是否占到一半左右，用来制造停顿？
- [ ] 句长是否以 25–40 字的中句为主，短句用于起头或收束？
- [ ] 加粗是否只用于小标题、定义句、结论句？每段是否不超过一处？
- [ ] 观点是否用"注意，X 不是 A，而是 B"这类句式，而非"我认为"？
- [ ] 连接词是否只用"所以／因此／也就是说／但是"这一套？有没有混进黑名单词？
- [ ] 有没有感叹号、表情符号、网络梗？（应当为 0）
- [ ] 术语首次出现是否给出"中文名（English，缩写）"？
- [ ] 中英文之间的空格是否全文统一，没有前后不一致？
- [ ] 引号是否只用来标记正在被定义的术语？
- [ ] 冒号是否用于下定义、引清单、给外文原名这三件事？

**引用与边界**

- [ ] 借来的比喻/框架是否点名机构+职位+人名？
- [ ] 概念归属是否引了一手文献？
- [ ] 文末是否有"参考链接"，格式统一？
- [ ] 是否写清了演示所依赖的具体对象（工具、平台、版本）？
- [ ] 数据是否标注了时效与版本？

**代码与图**

- [ ] 每段代码是否有引导句（全角冒号/句号结尾）和以"上面代码中，"开头的解释句？
- [ ] 代码是否最小化？截断处是否声明？
- [ ] 图是否紧跟相关段落，用"如下图""上图是……"与正文缝合？引用他人的图是否给出处？
- [ ] 图是否没有多余的图注？

**排版**

- [ ] 引用块里是否只有引语、清单、命令、代码，没有叙述段落？
- [ ] 正文是否以单独一行 `（完）` 结束？

**结尾**

- [ ] 是否显式收束（总结/行动建议/回译）？
- [ ] 结尾是否与开头的问题闭环？
- [ ] 正文结束是否标 `（完）`？

### 本规范对原站的收敛与补强（不是原站做法）

以下五条是原站**没有做到或前后不一致**的地方，本规范作了统一规定。它们属于规范性选择，不是对原站风格的事实描述：

1. **参考区标题统一为"参考链接"**。原站混用"参考链接""参考文献""参考网址"三种。
2. **勘误与更新机制**。抽样的文章正文中均无更新日志，存在事后补图补段而不声明的痕迹。本规范要求：正文实质性修改须在文末标注更新日期与内容。
3. **时效与版本标注**。原站的 DNS、TLD 服务器清单等时效性内容未标时间戳，全篇无软件版本号。本规范要求涉及版本、清单、命令输出、价格、性能的数据必须标注时效。
4. **标准文档引用**。原站讲协议的文章（如 DNS）未引 RFC 编号。本规范要求协议、格式、接口类文章必须引到标准文档。
5. **中英文空格与引号体例统一**。原站旧文中英文之间不加空格且同篇内不一致，引号用 ASCII 直引号。本规范要求全文统一加空格，引号统一为中文引号。

### 未能核实的部分

- 本规范未覆盖非技术类文章（散文、观点、译文），这些分类的写法与技术文章差异较大，不应混用同一套规则。
